# Spring Boot 性能优化

## 目标

先用可重复的工作负载和运行证据确认瓶颈，再实施可衡量、可回滚且不破坏正确性的优化。避免凭经验添加缓存、并发或复杂配置，也不把性能任务扩大为无关重构或升级。

## 工作流程

### 1. 明确目标和基线

- 先检查 git status、模块结构、运行配置、部署资源、监控指标、日志、追踪和已有 benchmark，保留用户已有修改。
- 明确目标指标、工作负载、数据规模、环境、采样窗口和验收阈值，至少记录延迟分位数、吞吐、错误率及相关资源。
- 执行测试、压测、profiling 或脚本前读取 .dev-env.yaml，按配置设置当前进程 Java 和 Maven 路径；不对生产环境执行未经授权的压力操作。

### 2. 定位实际瓶颈

- 沿请求、线程池、应用服务、事务、Repository 或客户端、数据库和外部系统链路定位耗时与资源消耗。
- 对数据库检查执行计划、N+1、索引、分页、连接池、锁和事务范围；对缓存检查命中率、失效、一致性和内存上限。
- 对 JVM 和并发检查 CPU、分配、GC、线程、阻塞、队列、I/O、序列化和启动阶段。
- 区分测量结果、根因假设和放大因素；没有基线时先建立观测，不直接提交猜测性优化。

### 3. 实施受控优化

- 一次聚焦一个主要瓶颈，优先采用现有基础设施和最小变更；保留开关、回滚路径和配置默认行为。
- 优化查询、批处理、缓存、连接池、线程模型或序列化时，同时检查事务、权限、幂等、顺序、数据一致性和错误语义。
- 只有在 Spring Boot 版本、部署模型和阻塞 I/O 场景明确适配时才使用 virtual threads 或其他 JDK 新特性。
- 不以牺牲正确性、可观测性、安全性或资源稳定性换取单一指标改善。

### 4. 验证收益和回归

- 使用与基线相同的工作负载、数据规模和环境，记录优化前后延迟分位数、吞吐、错误率、CPU、内存、GC、线程和数据库指标。
- 运行受影响的单元、Web、数据访问和集成测试，并检查并发、缓存失效、超时、降级和重复请求场景。
- 结果未达到目标时保留数据和结论，回滚无收益变更，不用主观判断宣称优化成功。
- 使用 Maven Wrapper；Windows 优先使用 mvnw.cmd，最后检查 git diff 和 git diff --check。

## 交付和边界

- 交付瓶颈证据、基线、变更、收益、资源代价、测试命令、未执行项、发布开关和回滚方式。
- 不对生产执行压测、profiling 或配置切换，除非用户明确授权且具备安全窗口和回滚方案。
- 纯代码整理使用 springboot-refactoring；JDK、Spring Boot 或依赖版本变更使用 springboot-upgrade-migration。
- 所有新增或修改文本使用 UTF-8；不执行无关的破坏性命令。

## 开发规范

- 直接调用本 skill 时，先读取项目根目录 `docs/开发规范/README.md`（存在时）和项目已有质量工具；不凭个人偏好添加风格规则。
- 由 `$orchestrator` 调用时，规范检查由 `development-standards` 阶段统一执行，本 skill 只遵循其报告和本任务专属约束。

## 编排契约

- 由 `$orchestrator` 调用时，按 Workflow Registry 指定的阶段执行，不重复执行其他阶段；直接调用本 skill 时仍执行完整优化流程。
- 支持阶段：`baseline`、`bottleneck`、`optimize`、`compare`、`regression`。
- 读取当前 run 中注册的输入 Artifact，将基线、瓶颈、优化和对比证据写入注册的输出 Artifact；不得使用未声明的路径传递上下文。
- 没有可重复基线或验证收益时保留事实和阻塞，不用主观判断宣称优化成功。
