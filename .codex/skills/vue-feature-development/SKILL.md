# Vue 3 功能开发

## 目标

以仓库事实、明确的交互契约和可验证的验收场景为依据，完成 Vue 3 前端功能从需求拆解、设计、实现到测试和构建验证的闭环。优先复用现有组件、组合式函数、Store、路由、API 客户端、样式和测试工具，不因个人偏好替换成熟约定。

设计与实现时遵守[通用设计与实现方向](../通用设计与实现方向.md)。

## 范围和边界

- 面向 Vue 3、TypeScript、Vite SPA；Nuxt、SSR、Nitro 和 Vue 2 迁移不属于本 skill 的默认范围。
- 新功能同时需要后端改动时，先确认现有 API 契约和用户授权；不在前端任务中擅自修改后端、数据库或公共接口。
- 纯缺陷修复使用 `vue-bug-fixing`；只读审查使用 `vue-code-review`；不改变行为的结构调整使用 `vue-refactoring`。
- 以测试、性能或生态升级为主要目标时，分别使用 `vue-test-development`、`vue-performance-optimization` 或 `vue-upgrade-migration`。

## 工作流程

### 1. 明确功能契约

- 将需求整理为目标用户、页面入口、输入、输出、状态变化、成功/失败反馈、权限、可访问性和验收场景。
- 区分必须实现、可选增强和明确不在范围内的内容；缺少且会影响实现的产品决策先记录并询问。
- 确认组件 props、emits、slots、路由参数、Store 状态/动作、API 请求响应和本地持久化键的兼容要求。

### 2. 保护并理解仓库

- 先检查 `git status`、用户已有 diff、前端根目录、`package.json`、锁文件、`pnpm-workspace.yaml`、Vite 配置、`tsconfig`、路由、Store、API 客户端和相似功能。
- 读取根目录 `AGENTS.md` 和 `.dev-env.yaml`；执行 pnpm、构建、测试或脚本前显式按 UTF-8 读取 `.dev-env.yaml`，使用 `frontend.package_manager` 的 `pnpm`，不修改系统环境变量。
- 如果脚本联动后端构建，按 `.dev-env.yaml` 的 `development.java.home` 和 `development.maven.home` 为当前进程设置 `JAVA_HOME`、`MAVEN_HOME`；单独前端命令不猜测或替换这些路径。
- 检查 `engines`、`.nvmrc`、CI 和现有 package scripts；Windows 优先使用项目已有的 `pnpm`/`pnpm.cmd` 约定，不猜测不存在的脚本。
- 记录现有目录、命名、导入别名、组件库、样式方案、错误处理和测试约定后再设计变更。

### 3. 设计数据流和边界

将功能表达为清晰的数据流：

`路由/用户事件 -> 组件边界校验 -> composable 或 Store -> API 客户端 -> 状态更新 -> UI/通知`

- 用 `<script setup lang="ts">` 和项目现有风格定义组件；优先使用类型化 `defineProps`、`defineEmits`，不直接修改 props。
- 将纯转换和领域规则放在可独立测试的函数或 composable 中；仅跨页面共享且确有必要的状态进入既有 Store。
- 明确初始、加载、成功、空数据、失败、重试和取消状态；异步请求要处理组件卸载、重复触发和过期响应。
- 复用现有 API 类型和错误转换；不得把服务端 DTO、内部状态和展示模型无边界地混用。
- 对表单明确字段类型、校验时机、提交幂等、键盘操作、焦点和错误提示；不只依靠按钮禁用表达错误。

### 4. 实现功能

- 遵循现有组件分层、组合式函数、Store、路由守卫、样式和国际化约定，只修改实现所需文件。
- 保持语义化 HTML、键盘可用性、可见焦点、标签关联、错误提示和现有响应式布局；不以视觉隐藏替代权限控制。
- 对不可信内容禁止直接使用 `v-html`；对 URL、用户输入、令牌和敏感数据遵循现有安全封装，不把秘密写入前端代码或日志。
- 不为一次功能引入新的 UI 框架、状态库、请求库或构建插件；确有必要时说明理由、版本、锁文件和回滚影响。

### 5. 编写分层测试

- 为纯函数、校验和 composable 逻辑编写快速单元测试；为组件验证 props、emits、插槽、用户事件、渲染状态和错误反馈。
- 需要路由、Store 或 API 时使用仓库已有的测试替身和集成方式；E2E 只在项目已经使用 Playwright/Cypress 时补充真实用户流程。
- 覆盖成功、空数据、加载、失败、重试、非法输入、重复提交、权限拒绝、路由参数变化和卸载清理等与需求相关的风险。

### 6. 验证并交付

- 先运行受影响的定向脚本，再按 `package.json` 中实际存在的命令执行 lint、类型检查、test 和 production build；不得把跳过测试的构建当作完整验收。
- 检查浏览器控制台、网络请求、生成产物和警告；必要时验证不同视口、键盘操作和错误网络条件。
- 检查 `git diff`、`git diff --check`、锁文件和变更范围，确认没有意外生成文件或依赖升级。
- 汇报功能契约、变更文件、接口/状态/配置影响、测试命令及结果、未执行项、环境阻塞和残留风险。

## 约束

- 不覆盖用户已有修改，不执行无关的破坏性命令或全量格式化。
- 不把“页面能显示”当作功能完成；必须核对交互、异常、权限、可访问性和测试证据。
- Vue、Vite、TypeScript 或相关库的 API 不确定时，使用 Context7（如果可用）或对应官方文档确认，并以仓库实际版本为准。
- 所有新增或修改文本使用 UTF-8；中文说明保持简洁，代码标识符和生态命令保留惯用写法。

## 接口文档门禁

- 若功能新增或修改对外 HTTP/Web API，调用 `$api-documentation` 更新 `docs/接口文档/${模块}-${功能}.md`；只保留一份当前文档，历史变化写入文档修订记录。
- 若功能不涉及公共接口，在交付结果或当前 run Artifact 中明确记录“无需更新接口文档”。

## 开发规范

- 直接调用本 skill 时，先读取项目根目录 `docs/开发规范/README.md`（存在时）和项目已有质量工具；不凭个人偏好添加风格规则。
- 由 `$orchestrator` 调用时，规范检查由 `development-standards` 阶段统一执行，本 skill 只遵循其报告和本任务专属约束。

## 编排契约

- 由 `$orchestrator` 调用时，按 Workflow Registry 指定的阶段执行，不重复执行其他阶段；直接调用本 skill 时仍执行完整功能开发流程。
- 支持阶段：`contract`、`inspect`、`compatibility`、`design`、`implement`、`test`、`verify`。
- 读取当前 run 中注册的输入 Artifact，将功能契约、设计、变更和验证结果写入注册的输出 Artifact；不得使用未声明的路径传递上下文。
- 修改阶段遵循用户授权和仓库边界；阶段失败时保留证据并报告阻塞，不把未运行的测试报告为通过。
