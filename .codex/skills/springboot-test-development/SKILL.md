# Spring Boot 测试开发

## 目标

以验收场景和风险为依据补齐可靠、可读、可重复的自动化测试，优先验证真实行为和失败路径。默认只修改测试及测试资源；需要修改生产代码时必须说明可测试性原因和影响。

## 工作流程

### 1. 了解测试和运行环境

- 先检查 git status、模块结构、构建配置、测试目录、测试命名、断言库、Mock 工具、Testcontainers 和 CI 测试命令。
- 读取被测接口、服务、Repository、配置、权限、消息或外部客户端，列出成功、边界、非法输入、异常和回归场景。
- 执行测试、脚本或构建前读取 .dev-env.yaml，按配置设置当前进程的 JAVA_HOME 和 MAVEN_HOME，检查路径和实际版本。

### 2. 选择最小合适的测试层级

- 纯领域规则和转换使用快速单元测试。
- MVC 或 WebFlux 路由、校验、状态码、响应和异常映射使用现有 Web slice。
- JPA、JDBC、迁移、约束和查询使用项目既有数据 slice 或 Testcontainers。
- 权限链路、完整自动配置、事务、消息或外部适配只在需要时使用范围明确的集成测试。
- 不用全量 Spring 上下文测试替代所有单元测试，不为了覆盖率数字测试无业务价值的实现细节。

### 3. 编写稳定测试

- 每个测试表达一个可读的业务行为，使用仓库已有 fixture、工厂、测试容器和断言约定。
- 覆盖成功、边界、非法输入、异常转换、权限拒绝、重复请求、并发或事务回滚等与需求相关的风险。
- 控制时间、随机数、线程和外部网络；优先使用时钟注入、确定性数据、等待条件和隔离的 stub。
- 不使用无界 sleep、不连接真实生产服务、不依赖测试执行顺序、不吞异常、不关闭失败断言。

### 4. 执行和分析

- 先运行受影响测试，再按仓库约定运行模块 test 或 verify；检查失败日志、资源清理、并行执行和重复运行稳定性。
- 对不稳定测试重复执行并定位共享状态、时序、端口、数据库、时区或环境依赖；不得简单增加等待时间掩盖问题。
- 需要跨 JDK 验证时，按 CI 支持矩阵执行；不能把单一本机通过报告为全部兼容。
- 检查 git diff、git diff --check，确认没有意外修改生产代码或生成文件。

## 交付和边界

- 交付新增或修复的场景、测试层级、执行命令、结果、未执行项和环境阻塞。
- 新业务功能的完整实现由 springboot-feature-development 负责；本 skill 只在测试目标独立或用户明确要求测试改进时主导。
- 如果测试暴露生产缺陷，记录复现证据；只有用户授权时才修改生产代码，并补充对应回归测试。
- 所有新增或修改文本使用 UTF-8；不执行无关的破坏性命令。
