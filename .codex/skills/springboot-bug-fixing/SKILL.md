# Spring Boot 缺陷修复

## 目标

以可复现证据和明确的回归验收为依据，定位现有 Spring Boot 缺陷的根因，实施范围最小且可回滚的修复。保持现有接口、数据、配置和运行约定，避免把排障任务扩大为无关重构或版本升级。

## 工作流程

### 1. 收集仓库和问题证据

- 先检查 git status、相关 diff、模块结构、构建配置、异常处理和相似代码，保留用户已有修改。
- 读取问题描述、日志、堆栈、请求响应、时间线、部署环境和失败测试；区分事实、推测和缺失证据。
- 执行构建、测试或脚本前读取根目录 .dev-env.yaml，按配置为当前进程设置 JAVA_HOME、MAVEN_HOME，并检查实际版本；不修改系统环境。

### 2. 建立最小复现

- 优先用现有失败测试、接口测试、集成测试或脱敏输入复现问题。
- 分离输入、状态、并发、时序、配置、数据和外部依赖因素；记录复现命令、环境和结果。
- 无法复现时，继续检查调用链、边界条件、异常转换、事务、线程、缓存和配置差异；不得用猜测替代结论，并明确当前限制。

### 3. 定位根因并设计修复

- 沿请求或事件、校验、应用服务、领域规则、Repository 或客户端、持久化和响应链路定位首个错误行为。
- 区分根因、放大因素和表面症状；先检查最近变更、兼容性约束和已有回归。
- 选择最小修复面，明确是否影响 API、数据、事务、权限、幂等、并发、配置和外部调用。
- 不顺手升级依赖、重排无关代码、改写数据库结构或引入新的抽象；确需扩大范围时说明理由和风险。

### 4. 实施并保护兼容性

- 遵循现有包结构、构造注入、异常格式、日志规范和事务边界。
- 同步补充能稳定复现原问题的回归测试；测试必须先失败后通过，或提供等价的证据。
- 对数据修复、迁移、缓存清理、配置变更或外部系统操作，明确幂等性、回滚方式和执行边界；不直接改生产数据。

### 5. 分层验证和交付

- 按影响范围运行单元、Web slice、数据访问、集成或完整 Spring Boot 测试；优先定向测试，再运行相关模块的 test 或 verify。
- 检查成功、边界、非法输入、异常映射、权限、重复请求、并发和历史回归场景。
- 使用 Maven Wrapper；Windows 优先使用 mvnw.cmd。检查 git diff、git diff --check 和实际变更文件。
- 汇报现象、根因、修复、回归测试、执行命令、通过或未执行项、环境阻塞和残留风险。

## 失败处理与边界

- 测试、依赖下载、JDK、数据库或外部服务不可用时，保留已有证据，提供替代静态检查，并明确不能证明的内容。
- 不为了让测试通过而放宽断言、吞掉异常、跳过校验或关闭安全控制。
- 不把“暂时不再报错”当作根因已确认；若只能提出假设，按假设交付并列出后续观测要求。
- 所有新增或修改文本使用 UTF-8；不执行无关的破坏性命令。

## 编排契约

- 由 `$orchestrator` 调用时，按 Workflow Registry 指定的阶段执行，不重复执行其他阶段；直接调用本 skill 时仍执行完整工作流程。
- 支持阶段：`evidence`、`reproduce`、`diagnose`、`fix`、`regression-test`、`verify`。
- 读取当前 run 中注册的输入 Artifact，将阶段证据写入注册的输出 Artifact；不得使用未声明的路径传递上下文。
- 阶段失败时保留原始证据并报告阻塞，不通过放宽断言、吞异常或跳过校验掩盖失败。
