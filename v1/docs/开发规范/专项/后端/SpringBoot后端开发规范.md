# Spring Boot 后端开发规范

## 1. 适用范围和版本

本规范适用于 Java + Spring Boot + Maven 服务。目标项目的 Java、Spring Boot、Maven、数据库驱动和中间件版本以项目配置和 `.dev-env.yaml` 为准；当前技能覆盖 JDK 8–25。执行命令前确认配置路径存在，并以实际 `java -version` 和 `mvn -version` 输出为准。

不得因为本文档存在就直接升级 JDK、Spring Boot、插件或依赖。升级必须作为独立的兼容性变更，记录目标版本、废弃 API、运行时差异、迁移步骤和回滚方式。

## 2. 分层和职责

推荐按项目现有架构保持清晰边界；名称可以不同，但责任必须可定位：

| 边界 | 主要职责 | 不应承担的职责 |
| --- | --- | --- |
| Controller/HTTP Adapter | 路由、协议转换、输入绑定、边界校验和响应映射 | 核心业务规则、复杂查询、事务编排 |
| Application/Service | 用例编排、业务规则、权限上下文、事务边界和外部协作 | 直接暴露持久化细节给 HTTP |
| Domain | 领域不变量、状态转换和可复用业务规则 | 依赖 Web、数据库连接或具体传输协议 |
| Repository/Data Access | 查询、持久化和数据映射 | 隐式修改业务状态或吞掉异常 |
| Infrastructure/Client | 外部服务、消息、缓存、文件和平台适配 | 把外部失败伪装成本地成功 |

实际项目已有分层优先；如果需要跨层调用，设计中说明原因、依赖方向和测试边界。

## 3. HTTP 契约和输入校验

- Controller 必须在系统边界完成格式、类型、必填性、范围和枚举校验；业务不变量由应用/领域层再次保护。
- 不信任客户端传入的用户 ID、租户 ID、角色、价格、状态或权限字段；服务端根据认证上下文和持久化数据重新判断。
- 区分参数缺失、格式非法、未认证、无权限、资源不存在、状态冲突和服务内部错误，使用项目既有错误格式和状态码。
- 请求对象、领域对象和持久化对象的职责应明确，避免直接把数据库实体作为公共 API 契约。
- 任何新增、修改、删除、鉴权、状态码、错误语义、幂等性或兼容性变化，都必须检查接口唯一文档。

## 4. 权限和数据访问

- 鉴权不能只依赖前端隐藏按钮或路由；后端必须在真正执行操作前验证身份、角色、租户和资源所有权。
- 权限判断应位于能够覆盖所有入口的边界，不能只在某个 UI 调用或单个 Controller 分支中实现。
- 查询和更新必须考虑越权、批量接口、导出接口、分页边界和并发状态变化。
- 默认拒绝高风险操作；权限失败不能泄露资源是否存在、内部路径、SQL、堆栈或敏感字段。

## 5. 异常和事务

- 异常转换责任必须明确：边界层负责协议错误，业务层负责业务失败，基础设施层保留可诊断原因并转换为稳定错误语义。
- 不捕获后静默忽略异常，不用成功响应掩盖部分失败，不把堆栈、SQL、密钥或内部路径返回给客户端。
- 事务边界应覆盖一个清晰的业务用例；事务提交前后的外部副作用、事件发布和缓存更新必须说明一致性策略。
- 避免在长事务中执行不可控的远程调用、文件操作或等待；必须执行时记录超时、失败和补偿策略。
- 重试必须有上限、退避、幂等性和最终失败处理；不能对非幂等写操作盲目重试。

## 6. 持久化和数据演进

- 查询必须明确过滤条件、排序、分页和空值语义，防止无界查询、隐式全表扫描和敏感字段误返回。
- 新增查询、索引或批处理应以执行计划、基线指标或其他证据说明必要性；不能仅凭猜测优化。
- 数据库变更必须说明前向兼容、旧代码兼容、部署顺序、回填方式、失败处理和回滚/恢复方案。
- 破坏性字段删除、类型收窄、重命名和非空约束应采用分阶段迁移，不能与依赖旧结构的代码同时上线。
- 数据库脚本、消息 schema、序列化字段和缓存键视为公共契约，不能只修改一侧。

## 7. 异步、消息和外部服务

- 异步任务必须明确触发条件、持久化状态、重复投递、失败重试、超时、取消和最终处理方式。
- 消费者必须具备幂等或去重机制；消息确认时机应与业务提交结果一致。
- 外部 HTTP、RPC、数据库和消息操作必须设置合理超时，并区分连接、读取、业务拒绝和不可重试错误。
- 断路、限流、降级、死信或人工补偿仅在项目已有能力或设计明确时采用，不用空泛机制掩盖缺少失败处理。
- 外部系统返回值必须在边界转换和校验，不能把第三方字段直接当作内部可信状态。

## 8. 配置、日志和可观测性

- 配置按环境注入，敏感值使用密钥管理或受控环境变量，不写入源码、默认配置、测试输出或 Artifact。
- 配置缺失、格式错误和不安全默认值应在启动或首次使用时明确失败；不能静默使用错误环境。
- 日志记录请求/任务关联标识、关键状态和耗时，但不得记录令牌、密码、完整个人数据、生产请求体或响应体。
- 错误日志应包含可定位的异常类型、操作和关联标识；相同异常不能在多层无意义重复打印。
- 重要业务操作应有可观测的成功、失败、延迟和重试指标；指标名称和标签不能包含高基数敏感值。

## 9. 性能和兼容性

- 性能优化必须先建立基线，再定位实际瓶颈，并用同口径数据证明收益和回归。
- 重点检查数据库查询、序列化、远程调用、线程池、连接池、缓存命中率和内存生命周期。
- 不以增加缓存、线程或重试次数作为默认优化；必须说明容量、失效、一致性和故障影响。
- 使用 JDK 或 Spring Boot 新特性前确认目标运行时、构建插件、容器镜像和部署环境均支持。
- 行为保持重构不得改变公共 API、数据语义、事务边界、错误语义和运行兼容性；变化应转为功能或迁移任务。

## 10. 后端验证清单

- 是否覆盖参数非法、未认证、无权限、资源不存在、状态冲突和依赖失败？
- 是否验证事务提交、回滚、重复请求、并发更新和异步重复消费？
- 是否核对 API 文档、序列化字段、状态码、错误格式和鉴权行为？
- 是否检查 SQL/查询范围、分页、索引、敏感字段和数据迁移顺序？
- 是否执行项目已有的 Maven 测试、`verify`、质量插件和集成测试；未执行项是否有真实原因？
