# 工程治理与协作流程

## 1. 目标和适用范围

本规范定义一次工程变更从提出到交付的最小可追溯流程，适用于功能开发、缺陷修复、重构、测试补充、性能优化、升级迁移和代码审查。

它不替代目标项目的业务规则、架构文档、构建配置或发布制度；当这些来源已经存在时，应优先遵守并在交付报告中引用。

## 2. 角色和责任

| 角色 | 责任 |
| --- | --- |
| 需求/业务负责人 | 明确目标、范围、验收条件、优先级和风险接受人 |
| 实施者 | 收集证据、保护契约、完成实现和验证，报告未执行项 |
| 审查者 | 以变更证据为基础检查正确性、安全性、兼容性、性能和可维护性 |
| Agent | 遵守用户和仓库规则，保留证据，不替用户扩大范围或隐瞒阻塞 |
| 维护者 | 维护规范、工具、Registry、Skill 和交付模板的一致性 |

同一人可以承担多个角色，但需求确认、实现判断和最终审查结论仍应在记录中区分。

## 3. 标准阶段

### 3.1 需求与范围

- 必须记录目标、成功标准、明确的非目标、影响模块和约束。
- 必须确认任务类型：功能、缺陷、重构、测试、性能、升级或审查。
- 必须识别是否涉及公共 API、数据库、消息、配置、权限、外部服务、缓存或用户数据。
- 不清楚且会改变实现方向的需求不得靠猜测闭合；应标为待确认或阻塞。

### 3.2 证据与现状

- 先读取目标项目 `AGENTS.md`、`.dev-env.yaml`、规范入口、构建文件、测试配置和相关契约。
- 检查 `git status`、目标 diff、用户已有修改和未跟踪文件；不得把无关修改当作本次任务内容。
- 以代码、测试、配置、日志、指标和外部系统状态为事实来源；代码样例和 Agent 常识只能作为低置信度建议。
- 记录当前行为、复现步骤、基线指标或兼容性约束。

### 3.3 契约与设计

- 先描述输入、输出、错误、权限、状态变化、事务边界、异步行为和兼容性，再决定实现结构。
- 对每个外部边界明确责任方：谁校验、谁鉴权、谁转换异常、谁提交事务、谁重试和谁记录指标。
- 设计应说明失败路径、幂等性、回滚方式和数据迁移顺序；无法安全回滚时必须提前说明。
- 涉及 API、数据库、消息、配置或序列化契约时，明确兼容策略和文档更新位置。

### 3.4 实现

- 只修改任务范围内的文件，优先采用最小、可审查的变更。
- 不进行无关全量格式化、批量重命名、依赖升级或目录重排。
- 不覆盖用户已有修改，不用 `git reset --hard`、`git checkout --` 等方式清理工作区。
- 新增或修改文本使用 UTF-8；脚本读写文件时显式指定 UTF-8。
- 任何删除、迁移、部署、外部写入或数据操作都必须确认目标、权限、幂等性和恢复方式。

### 3.5 测试与质量检查

- 按变更风险选择最小充分的测试层级，并覆盖成功、失败、边界、权限和回归路径。
- 先执行通用检查，再执行目标项目已配置的格式、Lint、类型、测试、构建和架构检查。
- 检查前重新确认规范来源和工具是否变化；需要时重新计算规范指纹。
- 未执行、失败、超时或环境缺失的检查必须单独记录，不能合并为“通过”。

### 3.6 审查与交付

- 交付前核对代码、测试、接口文档、数据库/消息迁移、配置和安全影响是否同步。
- 审查发现必须包含位置、事实证据、影响、严重级别和可执行的修复方向。
- 交付报告必须列出变更范围、实际执行命令、退出码、未执行项、环境阻塞、残留风险和回滚方式。
- 结论只对已验证范围负责，不把人工未核对内容或推测写成通过。

## 4. 变更风险分级

| 风险 | 典型范围 | 最低验证要求 |
| --- | --- | --- |
| 低 | 纯文档、内部重命名、无行为变化的局部重构 | UTF-8、diff 检查、相关静态检查或审查证据 |
| 中 | 业务逻辑、组件交互、配置、错误处理、权限展示 | 定向测试、失败/边界场景、相关构建或类型检查 |
| 高 | 公共 API、数据库/消息、鉴权、敏感数据、并发、外部写入、发布配置 | 契约验证、回归测试、迁移/回滚演练或明确的环境阻塞记录 |

风险按实际影响取最高级别，不因代码行数少而降低公共契约或安全变更的等级。

## 5. Agent 和 Artifact 交接

- 复杂任务使用 Registry 中已存在的 Workflow、Skill 和 Artifact，不凭记忆创建不存在的阶段或制品。
- Artifact 必须位于当前 run 目录内，使用 UTF-8，并记录来源、状态、证据和未完成项。
- 运行 ID 必须是安全的单层目录名；不能把用户输入未经校验地拼接成路径。
- 阶段失败时保留当前制品和原始错误，不删除证据，不自动重试有副作用的操作。
- `standards-context` 是检查基线，`standards-report` 是质量检查结果；规范指纹变化时必须重新发现。
- Artifact 是交接载体，不是业务真相；最终结论仍需由代码、测试和外部状态证据支持。

## 6. 完成定义

一次变更只有在以下条件均满足或被明确记录为阻塞时才可交付：

- 目标和范围清楚，非目标和风险已记录。
- 代码、配置、测试、接口文档和迁移文件与契约一致。
- 必要质量检查已执行并有真实结果。
- 未执行项、失败项、环境阻塞和残留风险已公开。
- 已说明回滚或恢复方式。
- 工作区没有任务范围外的新增、删除或格式化变更。
