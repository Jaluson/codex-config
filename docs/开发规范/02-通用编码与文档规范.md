# 通用编码与文档规范

## 1. 编码和文件操作

- 所有新增或修改的文本文件必须使用 UTF-8。
- 读取或写入文件时显式指定 UTF-8，不依赖操作系统默认编码。
- 不对与当前任务无关的既有文件进行批量编码转换、换行转换或格式化。
- 脚本处理用户输入时，必须区分文本内容、相对路径和命令参数，不能通过字符串拼接制造未校验的路径或 shell 命令。
- 生成临时文件或缓存时使用明确、受限的目录；不得把临时输出写入源码、Artifact 或配置的权威位置。

## 2. 格式、命名和注释

- 具体空格、换行、导入顺序、命名格式和日志字段优先遵循目标项目已经配置的工具。
- 未发现可靠工具或规则时，只报告建议或未知，不凭个人风格产生阻断。
- 新增项目文档和代码注释使用中文；代码标识符、第三方名称、协议字段、命令和 API 字段保留生态惯用写法。
- 注释解释原因、约束、兼容性或非显然的副作用，不重复翻译代码本身。
- 不为了满足风格偏好进行与任务无关的重排；任何自动修复必须由用户明确授权，并限定到已知工具和变更文件。

## 3. Markdown 文档

- 每个独立文档使用一个一级标题，标题层级不得跳跃。
- 规则文档应说明适用范围、强制级别、证据来源和失败处理，避免只列口号。
- 目录、文件名、命令、标识符和协议字段使用代码格式；命令示例必须能看出是示例还是当前仓库可执行命令。
- 相对链接优先指向唯一权威文档；链接目标被删除或移动时必须同步修复引用。
- 业务示例使用占位符和脱敏数据，不使用真实令牌、密码、手机号、生产 ID、请求体或响应体。
- 同一事实只保留一个最新来源；其他文档引用它，不复制容易过期的完整章节。
- 文档中的“已通过”必须对应实际执行证据；“未执行”“不适用”“环境阻塞”和“待确认”要分别表达。

## 4. YAML 和 JSON

### 4.1 Registry YAML

本仓库的 Registry 使用 `registry_tool.py` 支持的受限 YAML 方言：

- 缩进必须使用两个空格，禁止 Tab。
- 不使用锚点、别名、标签、多文档标记和不受支持的行内集合。
- ID 使用小写字母、数字和连字符，并遵守工具的长度限制。
- 文件路径必须是相对路径，不能是绝对路径或包含路径穿越；目标必须位于允许的仓库目录内。
- 新增 Skill、Workflow、Artifact 时同步更新对应 Registry、阶段契约、引用关系和测试。
- Registry 变更后必须运行 `registry_tool.py validate`，不能只依赖肉眼检查。

### 4.2 通用 YAML/JSON

- 配置字段必须有清楚的所有者、默认值、敏感性和兼容策略。
- 可能被解析为布尔值、数字、日期或特殊字符串的值应按项目解析器要求显式表达。
- JSON 不写注释；字段命名和空值语义遵循现有公共契约。
- 不把密钥、令牌、生产数据或个人敏感信息提交到配置、示例和测试夹具。
- 修改配置时同时检查读取方、默认值、环境覆盖、序列化和回滚行为。

## 5. Python 工具和脚本

- 本仓库现有 Registry 和规范检查工具只使用 Python 标准库；新增第三方依赖必须有明确需求、版本和安装边界。
- 文件读写显式使用 UTF-8；输出报告不得包含密钥、令牌、生产数据或未经脱敏的命令输出。
- 用户输入的路径必须解析并验证在允许根目录内；拒绝绝对路径、路径穿越和符号链接造成的越界目标。
- 外部命令使用参数数组和受控工作目录，避免拼接任意 shell 字符串；超时、非零退出码和启动失败必须区分记录。
- CLI 必须返回有意义的退出码，并让机器可读输出和人类可读输出表达同一结论。
- 异常信息应包含可定位的来源和上下文，不泄露环境变量、凭据或完整敏感输入。
- 新增或修改工具逻辑必须补充正常、非法输入、边界、失败和路径安全测试。

## 6. 依赖和配置变更

- 只有在需求、兼容性或安全修复需要时才新增或升级依赖。
- 依赖变更必须说明版本、来源、许可证/安全影响、兼容性和回滚方式。
- 不在业务代码中硬编码环境地址、密钥、令牌、数据库密码或部署专用参数。
- 环境变量、配置文件、密钥管理和默认值的责任边界必须清楚；本地默认值不能误用于生产。
- 变更依赖或配置后，执行目标项目已有的锁文件、构建、测试和安全检查；没有工具时如实记录未执行。

## 7. 变更安全边界

- 任何删除、移动、覆盖、迁移、导出或部署动作都必须先确定精确目标和恢复方式。
- 不使用仓库根目录、用户目录或未验证的环境变量作为递归破坏操作目标。
- 不把 Artifact、日志、测试输出当作长期存放敏感数据的地方。
- 不通过隐藏文件、未跟踪缓存或生成副本绕过规范、审查或唯一文档约束。
