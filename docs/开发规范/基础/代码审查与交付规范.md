# 代码审查与交付规范

## 1. 审查目标和顺序

审查以变更实际影响为中心，不以文件数量或个人风格为中心。建议按以下顺序检查：

1. 正确性：主流程、失败流程、边界、并发和状态转换。
2. 安全：认证、授权、输入、输出、注入、敏感数据和外部调用。
3. 契约：API、数据库、消息、配置、序列化、错误和兼容性。
4. 数据一致性：事务、异步、缓存、重试、幂等和迁移。
5. 性能和容量：查询、网络、线程、渲染、包体、内存和资源释放。
6. 可测试性和可维护性：职责、重复、命名、依赖方向、测试稳定性和文档。

具体格式差异只有在项目工具或明确规范支持时才形成违规。

## 2. 审查范围

审查开始前必须确认：

- 基准分支、提交范围、工作区状态和用户已有修改。
- 变更文件、未跟踪文件、生成文件和依赖/配置变化。
- 相关调用方、接口文档、测试、迁移、部署配置和外部系统。
- 目标项目的 `AGENTS.md`、`.dev-env.yaml`、规范入口和质量工具。

不能读取到的调用方、环境或外部状态应标为审查限制，不默认为没有影响。

## 3. 问题严重级别

| 级别 | 定义 | 处理 |
| --- | --- | --- |
| 阻断 | 会导致安全事故、数据损坏、公共契约破坏、核心功能错误或必要验证缺失 | 修复或由有权限的人明确接受风险后才能交付 |
| 高风险 | 可能在常见路径造成明显错误、越权、兼容性回归、严重性能问题或不可恢复副作用 | 默认要求修复并补充验证 |
| 一般 | 局部正确性、可维护性、测试缺口或可观测性问题 | 应修复；延期时记录原因和影响 |
| 建议 | 不影响当前行为的改进或低置信度风格建议 | 不单独阻断；不得伪装成强制规则 |

每条发现必须写出文件和行号/符号、事实证据、影响、复现或推理、修复方向和需要补充的测试。

## 4. 变更和提交要求

- 变更说明必须列出目标、范围、非目标、风险、契约影响和回滚方式。
- 提交/PR 不应混入无关格式化、依赖升级、重命名或生成文件；确需混合时拆分或说明原因。
- 代码、测试、接口文档、数据库/消息迁移、配置、监控和发布说明应保持同步。
- 不规定项目未采用的提交标题格式；遵循目标仓库已有约定，缺少约定时保持提交信息清晰、可搜索、描述实际行为。
- 交付前检查暂存区和工作区，确认没有密钥、生产数据、临时文件或未授权生成物。

## 5. 交付结论

交付报告必须包含：

- 实际变更摘要和文件范围。
- 目标环境、工具版本和配置来源。
- 已执行检查的命令、退出码、范围和证据。
- 未执行、失败、超时、环境阻塞和不适用项。
- API/数据契约文档更新结论。
- 安全、性能、迁移、发布和回滚影响。
- 残留风险、风险接受人和后续动作。

“通过”只对已验证范围有效；如果必要验证未完成，结论应为阻断、带条件交付或待确认，并明确条件。

## 6. Agent 交接要求

- 直接调用 Skill 时完成该 Skill 声明的完整流程；由 `$orchestrator` 调用时只执行当前 Workflow 指定的阶段。
- 优先读取已有 Artifact，不重复抄录前一阶段上下文；报告引用制品路径和来源。
- 阶段失败保留原始错误和当前状态，不删除证据，不隐瞒未完成输出。
- 不把未经验证的推断写入 `validation-report` 或最终 handoff。
- 使用模板时填写真实命令和结果；占位符必须替换或标记为待确认。

## 7. 最终审查清单

- 是否存在未覆盖的失败、边界、权限、重复、并发或竞态路径？
- 是否改变了 API、数据库、消息、配置、序列化或 UI 组件契约？
- 是否同步更新唯一接口文档、测试、迁移和发布/回滚说明？
- 是否泄露密钥、令牌、生产数据、个人信息、堆栈或内部路径？
- 是否执行了风险匹配的检查，并如实记录未执行项？
- 是否只有任务范围内的文件发生变化？
