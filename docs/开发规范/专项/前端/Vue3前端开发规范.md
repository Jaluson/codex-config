# Vue 3 前端开发规范

## 1. 适用范围和版本

本规范适用于 Vue 3 + TypeScript + Vite 单页应用。Vue、Vite、TypeScript、Vue Router、Pinia、测试工具和 Node 版本以目标项目配置为准；包管理器使用 `.dev-env.yaml` 和 `package.json` 中已声明的实际工具。

不得因为本文档存在就直接升级前端框架、构建工具或依赖。升级应单独记录兼容性变化、构建产物、浏览器支持、测试和回滚方式。

## 2. 组件和数据流

- 组件边界应围绕可复用职责、业务场景或视觉区域建立；页面编排、展示组件和数据访问职责应可区分。
- Props、Emits、插槽和暴露方法形成组件契约，必须定义清楚类型、必填性、默认值、事件语义和失败行为。
- 子组件通过事件表达意图，不能偷偷修改父组件对象或依赖未声明的全局状态。
- 可复用的状态转换、异步流程和副作用优先提取为 composable；与单个页面强绑定的逻辑不强行抽象。
- Store 只保存跨页面或跨组件需要共享的状态；短生命周期的表单、弹窗和局部加载状态留在组件边界。
- 服务端状态、缓存状态、用户输入和纯 UI 状态应区分所有权，避免多个来源同时写入同一事实。

### 2.1 变量和闭包

- 默认使用 `const`，包括 `ref`、`reactive`、数组和对象：只要变量绑定本身不重新赋值，就不得改用 `let`。
- `let` 仅用于确有重新赋值需求的局部变量，例如请求序号、循环控制、累积结果或可替换的缓存引用；声明范围限制在最小代码块内，不能用同一个变量承载不同语义。
- 业务源码禁止使用 `var`。生成代码、第三方代码和受其约束的兼容性文件不在此限，但不得把该例外扩展到新增业务代码。
- 闭包只捕获其完成职责所需的最小状态；回调优先通过参数接收临时数据，不能无意持有整页响应式状态、大型列表、DOM 引用或过期的 Props。
- 定时器、事件监听、订阅、Promise 回调和异步任务形成闭包时，必须在组件卸载、请求取消或状态失效后清理、终止或忽略结果，避免内存泄漏和旧请求覆盖新状态。
- 需要跨调用保存可变状态时，明确其所有者和生命周期，放入组件、composable 或 Store 的合适边界；不能用模块级闭包绕过状态管理、测试隔离或权限边界。

### 2.2 通用组件与 Element Plus

- 表单、表格、弹窗、分页、菜单、提示、加载、空状态等通用 UI，必须优先使用 Element Plus 已有组件、属性、插槽、事件和无障碍能力；不能为了统一命名或轻微样式差异重写等价基础组件。
- 只有 Element Plus 无法满足明确的业务语义、交互、性能或技术约束时才自建组件，并在设计或变更说明中记录原因、适用范围和替代方案。
- 跨页面重复且职责稳定的展示或交互模式应提取为通用组件；仅单页使用、需求尚不稳定或只存在表面相似时，保留在页面内，避免过早抽象。
- 通用组件必须具备明确、类型化的 Props、Emits、插槽和默认值；不直接依赖页面 API、页面 Store 或特定路由。业务组件可以编排通用组件并承载领域规则。
- 对 Element Plus 的二次封装必须保留必要的 `v-model`、插槽、事件、键盘操作和可访问性语义，不能通过不透明的配置对象、深层透传或隐式全局状态掩盖组件契约。

## 3. TypeScript 和 API 边界

- API 请求和响应必须有明确类型；无法确认的外部数据在边界解析和校验，不能通过大范围 `any` 隐藏不确定性。
- API 客户端负责协议调用、序列化和错误转换；组件负责展示状态，不在多个页面复制请求细节。
- 接口类型变化必须与后端契约和接口文档同步，尤其是字段可选性、空值、分页、状态码和错误结构。
- 用户输入、URL 参数、Storage、第三方脚本和后端响应都视为不可信来源。
- 类型断言必须说明为什么安全；不能用 `as`、非空断言或关闭检查来绕过未处理的空值和错误路径。

## 4. 路由、权限和交互状态

- 路由守卫可以改善导航体验，但不能替代后端鉴权；前端隐藏按钮不能作为安全边界。
- 路由参数、查询参数和回退路径必须校验，避免不可信 URL、开放重定向和越权展示。
- 异步交互至少明确初始、加载、成功、空数据、失败、重试和取消状态；避免请求竞态覆盖较新的结果。
- 表单必须明确校验时机、错误位置、提交中状态、重复提交、服务端错误和恢复方式。
- 新增或编辑/更新接口的前端表单必须提供字段用途说明或示例；新增与更新表单应覆盖同一业务字段及相同的必填、格式和长度校验，不能只校验新增表单。
- 接口字段的前端校验必须与后端 DTO、接口文档和业务契约保持一致；条件必填字段应随资源类型或业务状态动态启用校验，前端校验只改善体验，后端仍必须重新校验。
- 必填字段必须通过 Element Plus `required` 属性或 `FormItemRule.required: true` 形成可见的 `*` 标记；可选字段不得显示 `*`，错误信息仍须通过表单校验反馈。
- 可编辑的文本输入框必须设置简洁、可操作的 `placeholder` 示例或输入提示；`placeholder` 不能替代可见 `label`，只读或禁用的展示框不添加误导性占位提示。
- 破坏性操作应有清楚的确认、幂等或防重复机制，并在结果明确后更新本地状态。
- 全局错误处理不能吞掉局部上下文；用户提示应安全、可理解，调试细节写入受控日志而非界面。

### 4.1 用户触发的异步动作

- 保存、删除、状态切换、登录、查询、刷新和分页等动作必须有专属 loading 状态，并在 `try/finally`（或等价机制）中复位；失败、取消和异常均不得遗留禁用控件。
- 触发控件显示 loading 并防止重复执行。表单提交期间禁用表单、保存/取消和弹窗关闭入口；行操作期间禁用该行其他动作；查询、筛选和分页期间禁用对应参数控件。
- 表单校验失败不进入请求 loading 状态。写操作成功由页面显示一次动作级成功通知；同一次失败只由 HTTP 层或页面中的一个责任方显示一次错误通知；读取成功不提示，读取错误使用页面内错误状态或既有错误视图。
- loading 不能替代可访问性：按钮说明动作，禁用状态可感知，首次加载使用可见的骨架屏、遮罩或错误视图。
- 优先为页面动作建立稳定的动作键；Store 中的独立异步动作维护各自状态。新增异步入口的测试至少断言立即 loading、关联控件不可用、重复点击只发一次请求、成功或失败后状态恢复。

### 4.2 加载、通知与空状态

| 状态 | 必须呈现的反馈 | 行为边界 |
| --- | --- | --- |
| 首次加载 | 与最终布局接近的骨架屏，或明确的区域 loading | 使用 Element Plus 的 `ElSkeleton`、`v-loading` 等既有能力；不能以整页白屏代替加载反馈 |
| 局部刷新/筛选/分页 | 保留已稳定内容，并在列表、表格或触发控件显示局部 loading | 不重置无关区域，不让请求期间的布局大幅跳动，也不允许重复请求 |
| 写操作成功 | 一次与操作对应的成功通知，并同步更新可见数据 | 优先使用项目既有的 Element Plus 通知方式；同一结果不得由组件、Store 和 HTTP 层重复通知 |
| 失败 | 一次错误通知，必要时在相关区域保留可读错误信息和重试入口 | 不泄露调试细节；错误通知、内联错误与字段错误各自只承担其对应责任 |
| 空数据 | 明确区分“当前没有数据”和“筛选后无匹配” | 使用 `ElEmpty` 或项目已有空状态；筛选无匹配时提供清空或调整筛选的入口 |

- 骨架屏只用于内容结构和数据尚未知的首次加载或显著区域切换；短暂按钮操作、行操作和已加载数据刷新优先使用控件或区域级 loading，避免不必要地隐藏上下文。
- 任何 loading、成功、失败和空状态均须保持容器高度、键盘焦点和辅助技术语义可理解；通知不能成为页面状态的唯一记录。

## 5. 动画与动效

- 动效只用于解释状态变化、确认操作结果、维持界面连续性或引导注意力；不能以装饰为由延迟关键操作、遮挡内容或替代文字、图标和错误提示。
- 优先复用 CSS `transition`、Vue `<Transition>` / `<TransitionGroup>` 和 Element Plus 已有的动效能力。只有存在复杂时间线、手势驱动或跨元素编排等明确需求时，才引入 JavaScript 动画，并说明适用边界、资源成本和降级方式。
- 同一类交互使用一致的进入、离开和状态切换节奏；时长、缓动和延迟优先继承项目现有变量、组件默认值或设计系统。未定义统一来源时，新增动效应保持短促、可中断，并避免长时间循环或无意义延迟。
- 动效不能成为状态传达的唯一方式。必须尊重 `prefers-reduced-motion`：在用户请求减少动态效果时，移除或显著降低非必要位移、缩放、闪烁和自动播放，同时保留状态变化和操作结果的可见反馈。
- 优先动画化 `transform` 和 `opacity`，避免在高频交互或大列表中持续动画化会触发布局或重绘的属性。列表、路由切换、弹窗和加载态不得因动效造成明显卡顿、跳动、重复请求或焦点丢失。
- 动效开始、取消和结束后，交互状态、焦点、ARIA 语义和资源生命周期必须保持正确；组件卸载时清理计时器、监听器和由脚本创建的动画实例。

## 6. 响应式布局、动态铺满与视觉反馈

本节定义实现边界；页面层级、色彩和控件细节遵循 [Vue 前端 UI 设计规范](./Vue前端UI设计规范.md)。

- 布局优先使用 CSS Flex、Grid、`minmax()`、媒体查询或容器查询响应可用空间；不得依赖固定屏幕尺寸、负边距或由 JavaScript 反复计算窗口尺寸来勉强适配。
- 应用外壳和需要占满可视区域的业务页面使用动态视口高度（`100dvh`，并提供项目已有的兼容回退），剩余空间由 Flex/Grid 分配。可收缩子项必须允许收缩，业务内容在明确的内部容器滚动，而不是撑出浏览器页面滚动条。
- 不使用脆弱的固定高度或多层 `calc()` 推导内容区高度。只有 CSS 无法表达的尺寸依赖才测量容器，并使用 `ResizeObserver` 等受控机制；组件卸载时释放观察器和相关资源。
- 每个可操作控件都应有可区分的默认、悬停、焦点、按下、禁用和 loading 反馈；异步结果还应有成功、失败、空数据或无匹配状态。反馈与触发位置和操作含义对应，不能只依赖全局提示或颜色。
- 响应式切换、动态铺满、loading、空状态和错误状态不得造成内容跳动、横向溢出、焦点丢失、重复请求或不可点击的遮挡层。视觉反馈必须保留键盘和辅助技术可理解的语义。

## 7. 安全和可访问性

- 禁止把未经净化的内容直接交给 `v-html` 或等效 HTML 注入入口。
- 不可信 URL、下载地址、图片地址、iframe 地址和第三方脚本必须校验协议、来源和用途。
- 令牌和敏感数据的存储位置必须符合目标项目安全设计；不写入日志、错误上报、URL、查询字符串或不必要的持久化存储。
- 前端校验只用于体验，后端仍必须重新校验输入、权限和业务规则。
- 交互组件必须支持键盘操作、焦点管理、语义化标签和可读的错误提示；颜色不能是传达状态的唯一方式。
- 加载、错误、空状态和动态更新应对辅助技术可理解，避免焦点丢失和不可关闭的模态层。

## 8. 性能和资源生命周期

- 性能优化先记录首屏、交互延迟、请求耗时、包体或内存基线，再定位实际瓶颈。
- 按路由和功能边界进行合理的代码分割；不为了微小收益制造难以调试的动态加载。
- 长列表使用适合的数据分页或虚拟化方案；避免无界渲染、重复请求和不必要的深层响应式依赖。
- 组件卸载时清理定时器、事件监听、订阅、AbortController 和其他外部资源。
- 图片、字体、第三方脚本和缓存策略应考虑体积、来源、失败回退和隐私影响。
- 不通过全局缓存或持久化保存无法失效的用户数据；缓存必须说明生命周期和一致性策略。

## 9. 测试和前端验证

- 组件测试关注用户可见行为、交互、状态转换和错误路径，不依赖脆弱的内部实现细节。
- Composable、Store、路由守卫和 API 客户端应根据风险补充单元或集成测试。
- 至少覆盖表单校验、加载/失败/重试、权限展示、空数据、重复操作和接口错误。
- 接口新增与更新场景至少验证字段说明、`placeholder`、必填项 `*` 标记、非法输入阻止提交、合法输入提交以及校验条件切换后的恢复行为。
- 对每个用户触发的 `await` 检查成功、失败、loading、禁用和恢复反馈。
- 新增或修改动效时，验证正常模式和减少动态效果模式下的状态可见性、焦点、键盘操作和关键交互；性能敏感页面还应检查动画期间无明显掉帧、布局跳动或资源泄漏。
- 新增或修改页面布局时，至少覆盖常规桌面、窄屏、低高度、加载、空数据和错误状态，检查内部滚动、控件可见性、焦点与视觉反馈。
- 覆盖首次骨架、局部刷新、成功通知、失败通知、空数据与无匹配状态，断言通知不重复、数据和焦点按预期恢复。
- 测试不依赖真实网络、固定机器时间、随机顺序或未声明的全局状态；外部依赖使用可控替身。
- 执行目标项目已有的 lint、类型检查、测试和构建脚本，只使用 `package.json` 中真实存在的脚本。

## 10. 前端验证清单

- 是否清楚组件契约、状态所有权和 API 数据边界？
- 是否默认使用 `const`、仅在重新赋值时使用最小作用域的 `let`，且业务源码未使用 `var`？
- 闭包是否只捕获必要状态，并在卸载、取消或失效后避免旧结果写回与资源泄漏？
- 通用 UI 是否优先复用 Element Plus；自建或二次封装组件是否有明确业务边界、类型化契约和可访问性语义？
- 是否覆盖空值、加载、失败、重试、取消、重复提交和竞态请求？
- 新增/更新接口表单是否有字段说明和 `placeholder`，必填项是否显示 `*`，可选项是否不显示 `*`，且两种操作的校验是否一致？
- 是否为用户触发的异步动作提供专属 loading、禁用、防重复和恢复反馈？
- 是否按首次加载、局部刷新、成功、失败、空数据和无匹配选择正确反馈，并避免重复通知或白屏？
- 动效是否服务于状态变化并复用既有能力，且在减少动态效果模式下仍保持可用、可理解？
- 动效是否避免高频布局/重绘、焦点丢失、内容遮挡和资源泄漏？
- 响应式布局是否优先由 CSS 驱动，在窄屏、低高度和容器尺寸变化时不溢出、不遮挡？
- 需要动态铺满的页面是否使用受控视口/容器布局和内部滚动，而非固定高度或浏览器页面滚动？
- 控件和异步状态是否具备与位置对应、非仅颜色的视觉反馈，并保持键盘和辅助技术可理解？
- 是否检查前端权限仅用于展示、后端仍执行真实授权？
- 是否排查 `v-html`、不可信 URL、令牌持久化和敏感日志？
- 是否验证键盘、焦点、语义、错误提示和动态内容的可访问性？
- 是否执行项目已有的格式、Lint、类型、测试和构建检查；未执行项是否如实记录？
