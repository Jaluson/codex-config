# 接口与数据契约规范

## 1. 适用范围

本规范适用于对外 HTTP/Web API、前后端共享的数据结构、数据库字段、消息 schema、配置格式、缓存键和序列化协议。内部方法或仅用于实现的局部对象不自动形成公共契约。

代码、测试和实际运行行为是契约事实来源；文档不能反过来要求代码伪造未实现的行为。

## 2. 何时判定为契约变化

以下任一变化都必须进入接口/数据契约检查：

- HTTP 方法、路径、路径参数、查询参数、请求头或请求体变化。
- 请求字段或响应字段的名称、类型、必填性、默认值、空值语义或枚举变化。
- 成功状态码、失败状态码、错误格式、错误码或错误消息语义变化。
- 鉴权方式、权限范围、资源可见性、租户边界或脱敏行为变化。
- 幂等性、排序、分页、异步处理、重复请求或最终一致性行为变化。
- 数据库字段、消息字段、配置字段、缓存键或序列化规则变化。
- 删除、重命名、类型收窄、约束收紧或改变旧客户端可观察行为。

无法确认是否属于公共契约时，按高风险处理并记录待确认项，不直接假设“内部变化”。

## 3. HTTP API 唯一文档

- 目标项目的接口文档使用 `docs/接口文档/${模块}-${功能}.md` 作为模块-功能的唯一最新文档。
- 同一模块和功能不创建按日期、提交、环境或 HTTP 版本拆分的最新副本。
- 正文只描述当前真实行为；历史差异写入同一文件的“修订记录”，不复制整套历史接口章节。
- 首次建立使用 `R1`；每次实际契约变更递增修订号。该修订号不是 HTTP API 版本号。
- 无接口变化时也应在变更报告中明确记录“无需更新接口文档”。
- 更新前检查是否存在旧副本；只有确认有效内容已合并且唯一来源成立后，才可删除过期文件。

## 4. 最低文档字段

每个对外接口至少记录：

- 用途、业务前置条件和幂等性。
- HTTP 方法、路径、鉴权要求和权限范围。
- 路径参数、查询参数、请求头、请求体的名称、类型、必填性、约束和示例。
- 成功响应结构、字段语义、空值/缺省规则和状态码。
- 失败状态码、错误格式、错误码、可重试性和用户处理方式。
- 分页、排序、异步、超时、重复请求和最终一致性注意事项。
- 兼容性、弃用、迁移和客户端影响。
- 修订号、日期、修改内容、影响接口、原因和关联任务。

无法从代码、测试或运行证据确认的字段必须标为“待确认”，不能自行编造。

## 5. 兼容性演进

- 默认优先采用向后兼容的增量变更：新增可选字段、保留旧字段语义、兼容旧客户端和分阶段迁移。
- 删除、重命名、类型收窄、必填性收紧和错误语义变化必须有弃用通知、迁移窗口、调用方盘点和回滚计划。
- 读路径和写路径不应在同一时刻强制要求所有客户端升级；需要双读/双写时说明一致性和清理条件。
- 服务器必须对外部输入做完整校验，对未知字段、缺省字段和旧版本字段的处理遵循既有契约。
- 数据库、消息、缓存和配置变化必须与发布顺序、旧代码行为和失败恢复方式一起设计。
- 版本路径、媒体类型或协议版本只在项目已有策略或需求明确时使用，不能为了文档方便自行增加版本。

## 6. 错误和安全

- 错误响应应稳定、可机器判断且不泄露堆栈、SQL、内部路径、令牌或敏感数据。
- 不同原因需要不同客户端行为时使用稳定错误码或明确字段，不依赖可变的人类错误文本。
- 鉴权失败、资源不存在和资源不可见的语义按项目安全策略设计，避免越权探测。
- 示例只使用安全占位值，例如 `<ACCESS_TOKEN>`、`<RESOURCE_ID>` 和脱敏的假数据。
- 文档、测试夹具、日志和 Artifact 不得写入生产请求/响应、个人信息、密码或真实凭据。

## 7. 契约验证清单

- 文档中的方法、路径、字段、状态码和错误是否与实现及测试一致？
- 前端 API 客户端、后端 DTO、序列化配置和接口文档是否同步？
- 是否识别所有调用方、消费者、定时任务、缓存和导出链路？
- 是否验证旧客户端、重复请求、异常输入、权限失败和第三方失败？
- 是否说明迁移顺序、兼容窗口、清理条件和回滚方式？
- 是否只有一个最新文档，并在修订记录中保留本次变化？
